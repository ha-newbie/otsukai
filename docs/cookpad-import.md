# クックパッドの材料取込・買い物の除外設定

実装・確認日: 2026-10-15。

## 取込の範囲

レシピ →「レシピを取り込む」→「HTML・JSON」で、HTMLを貼り付けるかファイルを選ぶ。**「材料だけを取り込む」は初期状態で有効**。料理名・人数・材料名・分量・出典・URLを読み取り、作り方・写真・コメント・おすすめ料理は保存しない。調味料は削除せず材料として残す。通常の作り方も取り込む場合はチェックを外す。

クックパッドの公開レシピ1件（[確認ページ](https://cookpad.com/jp/recipes/20843981)）のHTMLで、`#ingredients`内の`li[id^="ingredient_"]`、材料名の`span`、分量の`bdi`、人数表示、著者欄、canonical URLを確認した。構造化Recipe JSONもあるが、名前と分量が分離したHTMLの材料欄を優先すると「ご飯」と「茶碗1杯」を別々に扱える。旧来の`.ingredient_row`内の名前/数量クラスも読み取り候補にしているが、旧版の実ページは未検証。

クックパッドのレシピURLを元URLまたはcanonicalから確認してから専用処理を使う。広告、調理手順、関連レシピ等の本文を走査して材料を増やさない。材料欄が不明なら構造化データへフォールバックしたことを表示し、両方なければ保存を進めない。壊れた材料行は、欠落した状態で保存せずエラーにする。

「●（A）しょうゆ」等のグループ記号は材料名から除き、同じ食材を共有できるようにする。未知の分量は推測せず適量にし、HTMLで名前と分量が分離している場合は分量を食材名に混ぜない。原表記は保存前の確認画面に残す。対応外の分量を専用フィールドで永続保存する機能は未実装なので、必要な場合は元レシピを参照する。

HTMLは画面へ挿入せず、接続しない`HTMLTemplateElement`の内容で材料欄だけを読む。スクリプト・画像・スタイル・iframe・イベントハンドラは実行/読み込みしない。ブラウザE2Eでも外部リクエストとスクリプト実行が起きないことを確認する。解析ライブラリ・サーバー・AI APIの追加はない。

## URL取得と利用条件

確認したページのレスポンスにCORSの許可ヘッダーはなかった。GitHub PagesのPWAから直接取得できるとは扱わず、今回の主経路は**ユーザーが利用条件上取り込めるHTMLを入力して端末内で解析**する方式。全レシピ・全HTML版の対応やサイトの許諾を保証するものではない。

通常のURL取得機能はCORS制約に従う。クックパッドのログイン、アクセス制御、有料表示、CORSを迂回しない。自動巡回や大量収集、制限回避用のプロキシは実装しない。[クックパッド利用規約](https://cookpad.com/jp/terms)の知的財産権・サーバー負荷・アクセス制御等の定めを確認し、取得できることと再利用の許諾を区別する。レシピの写真・手順を公開リポジトリへ転載していない。

## 買い物から除外する場所

**設定 →「買い物の集計」**で除外カテゴリを指定する。まずカテゴリ単位とし、初期値は「調味料」。取込時には塩・砂糖・しょうゆ等の既知名称を調味料候補にする。部分一致で「塩鮭」「塩昆布」を除外しない。曖昧なもの（例: バター）や未知の食材は自動で調味料にせず、確認時に選ぶ。

登録済み食材の分類は、同じ設定欄の「登録済み食材のカテゴリを変更」から修正する。IDを変えず、全レシピ・在庫に共通で適用する。取込画面の登録済み食材には現在のカテゴリを表示し、既存分類を勝手に上書きしない。

除外の意味:

- レシピにはすべての調味料と数量を保存する。在庫の使用予定にも含める。
- 除外は献立からの買い物生成だけに適用する。在庫割当の計算はそのまま行い、最終的な買い物行から除く。
- 設定変更だけでは既存リストを変更しない。次の生成、または買い物開始前の「献立から再集計」で反映する。
- 買い物中・完了済みの数量、手動調整、チェックは保持する。移行時も書き換えない。
- 買い足す調味料は「品目を追加」で直接追加できる。直接追加した品目は除外や再集計で消さない。

レシピ材料ごとの例外や食材ごとの除外フラグは未実装。カテゴリ方式で実際の運用を確認してから追加を判断する。

## 旧データ・バックアップ

DB名は`kosaji`を維持し、Dexie **v2**で設定に`excludedShoppingCategoryIds`を追加する。旧DBは既存カテゴリに調味料があればそれを初期値とし、なければ空配列へ移行する。レシピ・食材・在庫・買い物・購入チェックを変えない。新規DBの初期値も調味料を除外する。

バックアップはDBとは別管理の形式 **v2**。旧v1は旧スキーマで先に検証し、設定を補完してv2へ移行し、参照整合性を検証した後に通常の確認・復元へ進む。新形式での除外設定もバックアップ/復元する。存在しないカテゴリや重複指定、v1に新フィールドを混ぜた不正データは拒否する。旧アプリへ新v2バックアップを戻すことはできない。

## 検証と残件

計算: 調味料の数値/適量を買い物から除外しても在庫の予定残量を計算すること。保存: 開始前の再集計、直接購入品、開始後/完了後のチェック保護、カテゴリ参照、v1 DBの実アップグレードと再起動、v1/v2バックアップ復元を検証する。

画面: 構造だけを再現した自作HTML fixtureで、オフライン解析→材料名/分量/出典確認→保存→献立→調味料除外→設定解除→開始前の再集計→購入チェック→設定再変更→再読込を検証する。不正HTMLの保存防止、旧v1バックアップの購入チェック保護も含む。実サイトの本文/写真をfixtureへコピーしていない。

上記の公開ページから一度取得して一時保存したHTMLも、production buildのブラウザ画面で追加検証した。7食材を読み取り、作り方なし・元URL保持・保存成功・解析中の外部リクエスト0件を確認した。一時HTMLはソース配布・公開リポジトリへ含めない。

実機iOSでのHTMLファイル準備・貼付・ファイル選択・保存は別途確認が必要。ユーザーが使う個々のレシピ、HTML版の差、有料/ログインが必要なページは未確認。食材名の意味解析全般や網羅的な調味料分類は実装していない。
